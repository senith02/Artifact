Read this first

This project is not simply building an ML model, and it is not a build-duration prediction study. The comparison that matters is whether extra SE information gives meaningful incremental value over a duration-only control. A null answer ("it does not") is a legitimate, predeclared outcome. It would not mean SE characteristics are useless everywhere: conclusions are limited to this dataset, these 28 features, and this protocol.

03 · motivation

The problem, why it matters, and the gap

The problem

Every push to a CI system starts builds and tests. Carbon-aware computing moves flexible work to hours when grid electricity is cleaner. CI feedback is supposed to be fast, though, so delaying every build to save carbon slows developers down. A selective scheduler has to decide which builds should wait.

Why it matters

The accounting model used here makes energy proportional to build duration: a long build run at a dirty hour wastes the most carbon. Expected duration is therefore the natural, cheap selection signal, and the one any practitioner would try first. Adding a commit-level SE model costs data plumbing, training, calibration, monitoring and explanation. The practical question is whether that extra complexity is justified.

The research gap

The thesis draft (Chapter 2) states the gap as an integration gap. Carbon-aware scheduling work mostly asks when to run already-selected workloads. Empirical SE work shows commit characteristics predict build failure and duration. Few studies combine the two to ask whether commit-level SE characteristics carry decision value beyond expected duration for selecting builds. Layer 0-A frames the contribution the same way: a value-of-information study and an evidence-derived policy, not a new scheduling algorithm.

Not yet verified

Literature claims and inherited figures in the thesis draft have not been checked against their original sources. That is task P5-T1 (dissertation/reference_audit.md). Until then this guide repeats no literature numbers.

Why the rule is fixed in advance

With nearly a million builds, almost any difference is statistically significant. The protocol therefore requires a practical floor (ΔPR-AUC ≥ +0.01 at model level; ≥ 5% TTFF p95 or ≥ 1% carbon at matched points at decision level), and it was written before any model was trained. The floors cannot be relaxed after a result is seen (eval_protocol.md §A1.7).

05 · components of the study

The seven building blocks

These are easy to confuse. Each does one job, and several are deliberately kept apart.

A · Duration-history control (d̂)

A commit-time estimate of how long the build will take, from the project's own earlier builds (④b, primary) or a regressor (④a). The null every SE signal must beat.

Do not confuse with

The build's actual duration. That is unknown at decision time and is never an input.

B · SE-aware modelling

Calibrated failure-probability models using d̂ plus 28 commit features in six families. They are the treatment, tested for incremental value.

Do not confuse with

The contribution itself. The model is a candidate signal. The contribution is the value-of-information finding.

C · Eligibility (Stage 1)

Deterministic rules on PR status and branch name decide which builds may wait at all. There is no ML here, ever.

Do not confuse with

Deferability. The rules approximate it; the data has no "safe to delay" label (§15).

D · Carbon accounting

E = 42.5 W × duration; carbon = E × the grid intensity of the scheduled hour. Applied after the decision, for scoring only.

Do not confuse with

Measured emissions. These are estimates.

E · Scheduling policy

decide() runs Stage 1, then Stage 2 under policy_spec.yaml: defer if d̂ ≥ d_threshold, to the greenest hour within W_max.

Do not confuse with

A scheduling algorithm contribution. The policy is deliberately simple and evidence-derived.

F · Replay evaluation

Historical builds replayed through six strategies on identical inputs, sweeping each strategy's aggressiveness to trace a frontier.

Do not confuse with

A live deployment. Arrivals are from 2011–2016 and carbon is a 2024–2025 profile.

G · Final held-out evaluation

Phase 3 opens the 170 test projects once, against the frozen policy, to confirm or overturn the calibration findings.

Do not confuse with

Calibration results. Everything on this page before P3 is calibration evidence.

06 · data

Data: what is used and how it is prepared

TravisTorrent, release final-2017-01-25: Travis CI builds joined with GitHub metadata, one row per build job, 66 columns, four languages. It is the single backbone dataset (invariant 2): it trains the models and drives the replay. Builds span 2011-04-16 to 2016-08-31. The label is tr_status (failure = failed or errored; canceled builds excluded).

Preparation steps, in order

  1. Header check. The loader validates the CSV header verbatim against context/dataset_reference.md. The paper's Table 1 uses different names and is never trusted (DL-002).
  2. Grain. Aggregate job rows to builds. Duration uses the max over jobs (DL-009, DL-010).
  3. Cleaning funnel. Drop builds without a usable label, exclude canceled builds, reject unparseable timestamps, and record rows in and out at each step.
  4. Features. 28 commit-time features in six families, with outcome columns blocklisted. {{evidence.features.verdict_counts.constant}} features turned out constant and {{evidence.features.verdict_counts.near-constant}} near-constant (DL-016); they are kept and reported, not silently dropped.
  5. Split. Whole projects are assigned to train, calibration or test (§07).
Data-quality findings that limit conclusions

Fully-null columns: {{evidence.data.fully_null_columns|join}}. git_diff_test_churn is zero in every build, so test_churn and test_density_ratio are constant. F2 keeps only {{evidence.features.family_effective.F2.effective}} of {{evidence.features.family_effective.F2.members}} effective members. There are no commit messages, so no fix-keyword feature (DL-015). A null for a weakened family is partly a data limitation, which is why the result is read as a lower bound.

07 · validity guard

How leakage is prevented

Leakage means a model sees information it could not have at decision time, so it looks better on paper than it would in real use. This project blocks it in four independent ways.

1 · The current build's duration never reaches a decision

tr_duration is an outcome. It has exactly three permitted roles: simulator accounting, historical labels for d̂ (earlier builds only), and a labelled oracle bound. decide() raises an error if handed it.

Why

Otherwise "beyond expected duration" would secretly mean "beyond the real duration", which no deployment can know.

2 · Outcome columns are blocklisted in code

tr_status, test counts, log durations and tr_prev_build fail an assertion if they reach any feature matrix, with negative tests that inject them on purpose.

Why

A human rule can be forgotten; a failing test cannot.

3 · History is strictly causal

④b uses only the project's builds that started strictly before the one being scored. Ties and the future are excluded. Fitted parameters come from train projects only (DL-014).

Why

That is the information a deployed scheduler would really hold: its own repository's history to date.

4 · Projects are split, not builds

{{evidence.splits.train.projects}} / {{evidence.splits.calibration.projects}} / {{evidence.splits.test.projects}} projects, disjoint, frozen at sha256 {{evidence.splits.sha256|short}}…. The test split has been dropped unread by every script so far.

Why

A model that has seen a project's builds can memorise its habits. Held-out projects measure generalisation to new repositories.

Do not confuse

Calibration projects are used to fit calibrators, choose forms and fit the policy. Test projects are used once, in Phase 3, and nothing is re-fitted afterwards. Using calibration is not "peeking"; using test before P3 would be.

08 · experiment

How the experiments are designed

Altitude 1: model level (done on calibration)

In
train split, d̂, 28 features in F1–F6
→
Out
ΔPR-AUC of {d̂+Fᵢ} vs {d̂}, 95% paired-bootstrap CI (B = 1000)

Six arms were trained, one per family, each identical except for its feature set, plus the {d̂} control and the {d̂ + all 28} full arm. A family passes model level only if its CI excludes 0 and its gain is at least +0.01.

Altitude 2: decision level (P3-T3, on test)

In
identical replay trace, strategies ④a, ④b, ⑤ swept over d_threshold × W_max
→
Out
frontiers in (carbon saved, TTFF p95); matched-point deltas; area between frontiers with CI

Carbon saved is proportional to duration by construction (§A1.13), so strategy ④ always leads on raw carbon. SE value could only show up as better failure-feedback time (TTFF) at the same carbon. The two strategies are therefore compared along their whole trade-off curves, never at a single point (DL-013).

14 · two different things

Research experiment vs practical artifact

The research experiment

Evaluates the duration control, the SE-aware models, the six feature families, the model arms, six replay strategies, decision outcomes (TTFF, latency) and estimated carbon, all on historical traces with a frozen protocol. This is where the findings come from.

The practical artifact

A developer-facing GitHub Actions decision-support tool (Phase 4) that runs the same decide() and the same frozen spec. It demonstrates the finding end to end. It is not evidence of real-world carbon savings. None of it exists yet.

The intended artifact concept

As described by the author on 2026-09-25. Steps marked "not in plan" are not in development_plan.md today.

Region detection is an estimate

If region inference by IP address is added, it gives an estimated region for the runner, never data-centre ground truth. The current plan instead uses the UK national carbon series with a cached fallback. Adding region inference changes the P4 contract and needs a decision-log entry.

Not redesigned yet

The review report recommends narrowing P4 if the null survives (no 28-feature request schema, no SHAP panel, team-declared urgency). The plan says that decision is taken after P3-T5 and before P4-T1. This guide shows the plan as it stands.

15 · construct validity

Deferability: the most important limitation

TravisTorrent records what happened to each build. It does not record whether a build was acceptable to delay. There is no column saying "this build could safely have waited". Everything about "which builds may wait" is therefore an experimental definition, not a measurement.

Eligibility is an approximation

Stage 1 marks PR builds and pushes to mainline, release, stable, hotfix or version-like branches as non-deferrable, and everything else as deferrable. Manual and scheduled/nightly builds have no marker at all (DL-020), so the deferrable set is entirely "pushes to unprotected branches".

Failure is not urgency

A passing build can be release-critical. A failing build is not automatically safe to postpone; delaying it delays exactly the feedback CI exists to give. The failure model predicts outcomes, not business priority.

The validator proves consistency, not correctness

0 violations means no rule-non-deferrable build was deferred. It does not mean the rule identifies genuinely safe builds. The approximation's error rate is unmeasurable in this corpus.

What a real tool should do

Treat urgency as an explicit team policy: branches, workflows, labels, environments and a maximum delay declared by the team. Do not infer it from historical failure data.

16 · boundaries

What this research does not prove

Three different situations, kept apart. Tested and found null means the experiment was run and the effect was not there. Not tested means no evidence either way yet. Known limitation means the design cannot answer it.
